# Issue #214 — secret cutover acceptance and operator evidence

## Status

This document prepares the deployment acceptance for
[Issue #214](https://github.com/mojtaba-arvin/video-service/issues/214).
It is an operator procedure, not evidence that a deployment was inspected.
No production AWS account, deployment shell, broker, Redis, PostgreSQL, or
object-store credentials are available to this repository workflow.

**Keep `WORKFLOW_DURABLE_DISPATCH_ENABLED=false`.** Do not schedule/start the
outbox relay for durable dispatch, switch CreateJob to `durable_vod_v1`, or
enable production secret resolution on the strength of CI or this document.

## Repository-side facts and gaps

The repository implementation/configuration establishes the following code-level
facts; none substitutes for a live deployment test:

- CreateJob encrypts callback and optional signing material with a fresh
  AES-256-GCM DEK generated by AWS KMS, and persists the envelope with the Job
  and immutable plan transaction. Plan data receives opaque secret references.
- The worker calls STS GetCallerIdentity, checks the configured assumed-role ARN
  prefix, fetches the envelope for the exact Job/worker/purpose/reference, then
  decrypts it. Missing configuration, STS/KMS failures, identity mismatch,
  scope mismatch and decryption failure are fail-closed paths.
- Redis Job details are built from non-secret status metadata; the callback
  destination is not copied into that projection. The secret resolver is not
  passed as a Celery task argument.
- `WORKFLOW_SECRET_KMS_KEY_ID`, `WORKFLOW_SECRET_KMS_REGION` and
  `WORKFLOW_SECRET_WORKER_ROLE_ARN_PREFIX` are explicit configuration.
  There is no local/static production key fallback.
- `WORKFLOW_DURABLE_DISPATCH_ENABLED` defaults to false and selects the
  legacy Celery path when false.
- The current key-provider adapter exposes GenerateDataKey and Decrypt. No
  repository-side secret rewrap/re-encryption lifecycle operation was found.
  AWS KMS automatic rotation of a symmetric key and migration/re-wrapping
  envelopes to a different KMS key are different operations; do not claim the
  latter is implemented.

Still unproven: deployed role identities and trust policies, key and bucket
policies, actual S3 access boundaries, live encrypt/decrypt, key-rotation
behavior, real legacy Job inventory, deployed log/trace redaction, and
dependency-outage behavior in the target topology.

## Gate A — immutable target and identity inventory

Run only from the authorized staging deployment/operator session. Use a
dedicated non-production account and synthetic callback values. Do not paste
credentials, plaintext callback URLs, ciphertext, wrapped DEKs, signed URLs,
or decrypted material into a terminal transcript, ticket, artifact, log, or
this repository.

Record:
- environment/account ID and AWS region;
- source commit and immutable image digest for API, callback worker, general
  Celery worker, migration job and scheduler;
- deployment revision and time; configuration *names and non-secret values*
  (key ARN/alias, region, expected assumed-role ARN prefix, bucket names and
  approved prefixes);
- API workload role, callback-worker role, general-worker role and their trust
  relationships; policy document revision/hash and key policy revision;
- operator identity and evidence artifact locations.

From each deployed workload identity (not an operator's personal shell), run
STS GetCallerIdentity and compare the returned account/role with the approved
role inventory. The callback worker must match the exact configured assumed-role
prefix. A prefix match in application configuration is only an additional
guard; IAM trust and resource policies remain authoritative.

**Pass condition:** API and callback worker identities are distinct where
required; the worker cannot obtain credentials by caller-supplied ARN or task
argument; trust is restricted to the intended workload; no broad fallback role
is available. A role name copied from IaC without a live STS observation is not
evidence.

## Gate B — KMS envelope and key policy

Use a synthetic callback destination served by a controlled staging receiver.
Exercise the real CreateJob encryption path and real worker resolution path.
Verify both `webhook.callback` and `webhook.signing` purposes where signing
is enabled.

Required authorization boundaries:
- API role: `kms:GenerateDataKey` on the exact configured symmetric key;
  no `kms:Decrypt` unless separately justified and approved.
- Callback worker role: `kms:Decrypt` on that exact key, constrained by
  encryption context; no `kms:GenerateDataKey` unless separately justified.
- Key policy and IAM conditions constrain `purpose`, `algorithm=AES-256-GCM`,
  `job_id`, `tenant_id`, `issuer`, `subject` and `secret_id`.
- Do not broaden the callback role to unrelated secret purposes or general
  application KMS administration.

Positive tests:
1. Create a synthetic Job with a callback and resolve/deliver it through the
   deployed callback worker.
2. Repeat for the signing secret if configured.
3. Confirm KMS CloudTrail events show the intended role, key and encryption
   context (retain event IDs, not request payloads containing sensitive data).
4. Confirm the callback receiver receives the expected signed request without
   exposing the secret to the caller, broker or observability pipeline.

Negative tests must deny wrong role, wrong key, missing/extra encryption
context, wrong purpose, wrong Job/tenant/issuer/subject, unknown/expired/revoked
reference, disabled key and unavailable STS/KMS. The Job must remain durably
queryable; delivery must fail closed with a stable redacted failure classification.
No plaintext or alternate-Job fallback is allowed.

### Rotation acceptance

Distinguish these operations explicitly:

1. **AWS KMS automatic rotation of the same symmetric customer-managed key:**
   record key rotation enabled/status and rotation policy; after a scheduled
   rotation has actually occurred in the staging account, prove that a newly
   encrypted envelope decrypts and that a pre-rotation envelope still decrypts
   during the approved retention/overlap period. Do not simulate a completed
   rotation merely by toggling a setting.
2. **Migration to a different KMS key/key ARN:** this requires an explicit,
   audited envelope rewrap/re-encryption lifecycle that preserves authenticated
   context and atomically updates the envelope. The current repository adapter
   does not expose that operation. This gate is **not passable** until that
   capability is implemented and tested, or the owner explicitly limits the
   supported rotation contract to same-key AWS automatic backing-key rotation.

Never disable or schedule deletion of an old key while any retained envelope
depends on it. Keep old key material available through the maximum callback
retry, Job retention and recovery horizon. Record key IDs/versions and outcome
only, never DEKs or plaintext.

## Gate C — S3 least privilege

Test the actual API, media worker and publication worker identities separately.
Derive the permission matrix from the exact code paths and observed staging
requests; do not copy a broad managed policy as a shortcut.

For each identity, record the exact buckets, prefixes and required operations
(read/head, list constrained by prefix, multipart create/upload/complete/abort,
conditional object create, read-back and cleanup/delete only where required).
Deny access to:
- another tenant's prefix/bucket;
- unrelated buckets and prefixes;
- bucket policy/configuration administration;
- ACL/public-access changes and unrestricted listing;
- object deletion/overwrite when the workflow contract does not require it.

Exercise normal upload, multipart completion, conditional no-replace conflict,
read-back checksum/size validation and authorized cleanup under the deployed
identity. Also run explicit denied-access probes outside the allowed prefix.
Capture request IDs and allow/deny decisions, not signed URLs or object
contents. Confirm bucket encryption, public-access block, versioning and
lifecycle/retention controls against the approved deployment policy.

**Pass condition:** every successful operation is required by the workload;
out-of-scope operations are denied; no worker has wildcard bucket/object
permissions or cross-tenant access. IAM policy simulation alone is supporting
evidence, not a substitute for real signed requests under the workload role.

## Gate D — legacy Job and Redis callback drain

Do not start a cutover until the operator produces a point-in-time inventory
from the authoritative PostgreSQL state plus the deployed broker, workers and
Redis compatibility projection. Never export callback values.

Inventory at minimum:
- every accepted legacy-backend Job, owner/tenant state, creation time,
  terminal/non-terminal state, cancellation state and last durable transition;
- queued, reserved, active, scheduled, retrying and orphaned Celery task IDs;
- callback-required flag, callback delivery state/attempt count and whether
  the legacy Redis `JOB_DETAILS` entry is present/expired (boolean only);
- related Stage/Attempt state, source/output Artifact publication state and
  completed external side effects;
- worker image/capability version and maximum task/job/retry lifetime.

Classify each Job, without reading callback material into the report:
- **Terminal and reconciled:** all required outputs and callback outcome are
  durable; retain according to policy.
- **Queued/reserved but not started:** stop new legacy admission only in the
  approved maintenance window; allow the existing worker to finish or cancel
  through the supported durable cancellation path.
- **Running/retrying:** keep on the compatible legacy worker until terminal;
  do not replay on the durable executor concurrently.
- **Callback pending/ambiguous:** preserve the legacy worker/cache path while
  the approved retry horizon remains; reconcile from delivery history and
  receiver acknowledgement where available. Never invent or backfill an
  expired callback URL.
- **Missing Redis details or unknown owner:** quarantine from automatic
  migration; resolve through an explicitly authorized operator/business
  procedure. Do not infer ownership from request metadata or reference IDs.

Safe drain sequence:
1. Freeze the inventory timestamp and record counts by category, worker
   version, age bucket and callback state; store only IDs in access-controlled
   evidence, never callback URLs or secret values.
2. Stop admission to the legacy path only after the release owner approves the
   maintenance window. Keep existing legacy workers alive and prevent new
   durable-plan messages from reaching workers without the required capability.
3. Drain queued/reserved/running/retrying work on its original compatible path.
   Do not dual-dispatch, bulk-replay, bulk-convert, or delete Redis keys.
4. Reconcile each non-terminal Job against PostgreSQL Job/Workflow/Stage/Attempt
   state, artifact publication/read-back, cancellation and callback delivery
   history. Record an explicit disposition and operator for every exception.
5. Confirm no ambiguous active Job remains, callback retry windows have elapsed
   or have an approved disposition, and no legacy callback reads are observed
   for the agreed observation period.
6. Only then approve the separately controlled durable-dispatch cohort. Retain
   a stop switch and a path for already-running legacy work.

The report must contain counts, age distributions, exception IDs in a restricted
system, dispositions and reviewer sign-off. It must not contain callback
destinations, query strings, signing keys, signed URLs or copied Redis payloads.

## Gate E — secret isolation and redaction

Use synthetic canary secrets with unique non-production markers. Capture each
boundary in a controlled test harness and assert the marker is absent from:
- serialized immutable plan and plan snapshots;
- outbox payload JSON and database event payloads;
- Celery message body, headers, kwargs and result backend;
- Redis Job details/status projections and cache snapshots;
- application, worker, broker, KMS diagnostic and audit logs;
- OpenTelemetry spans, span attributes/events, exception text and metric labels.

Assert that only the opaque reference is present where the contract permits it.
Also assert ciphertext/wrapped DEK are confined to the encrypted database
envelope and never copied into plan/outbox/broker/cache/log/trace payloads.
A secret value must be resolved only inside the authorized delivery worker,
immediately before use, and never attached to exceptions or retry state.

Run cross-Job, cross-tenant, wrong-purpose, wrong-subject and wrong-adapter
resolution probes. All must deny without revealing whether another tenant's
secret exists. Review actual deployed log and trace sinks, not only unit-test
logger mocks.

## Gate F — dependency outage and recovery matrix

Run in staging with durable dispatch still disabled for the legacy path, then
exercise the secret path independently. Preserve durable Job/Workflow state.

| Injected condition | Expected behavior | Required evidence |
|---|---|---|
| KMS GenerateDataKey denied/unavailable | New callback-bearing submission rejected before acceptance; no plaintext fallback or partial Job/secret transaction | API result, DB transaction outcome, redacted KMS event |
| STS unavailable or wrong assumed role | Worker refuses secret resolution; no callback attempt using fallback identity | Worker outcome, STS event, Job remains queryable |
| KMS Decrypt denied/unavailable | Callback delivery fails closed; no secret in task state, exception or logs | Redacted error classification, KMS event, unchanged envelope |
| Secret missing, expired, revoked or scope mismatch | Non-retryable security/configuration failure unless provider classifies transient outage; never resolve another reference | Resolver result and durable delivery/Job state |
| Callback DNS/connect/read timeout or receiver outage | Bounded retry according to delivery policy; stable Delivery ID; no unbounded task or plaintext fallback | Attempt history, retry bound, receiver dedup evidence |
| Redis callback projection missing/expired | No secret recovery from Redis; new secret path remains resolvable from durable envelope; legacy Job follows explicit quarantine/reconciliation | Redis key presence boolean, DB state and disposition |
| Worker process loss during callback | Reconcile delivery ambiguity using stable Delivery ID and receiver dedup; do not claim exactly-once | Worker restart evidence, sender history and receiver transaction evidence |

A transient dependency outage may be retried only within the configured bounded
policy. Authorization, context, tampering, expiry and malformed-envelope
failures must not be retried as if they were transient. Do not acknowledge a
callback as delivered without the required durable delivery receipt/state.

## Gate G — evidence and sign-off

For every gate record:
- exact source SHA and immutable image digest for every participating service;
- environment/account/region and timestamp;
- operator identity and workload role identity (ARNs are non-secret);
- non-secret configuration and policy revision/hash;
- test case, expected result, observed result and pass/fail;
- redacted log/trace/CloudTrail/dashboard evidence reference;
- incident/change ticket, reviewer and explicit sign-off.

No evidence artifact may include credentials, secret values, plaintext callback
URLs, signed URLs, ciphertext blobs, wrapped/plain DEKs, raw Redis payloads or
unredacted request/response bodies.

## Required owner action before this can be executed

A deployment owner with authorized access must provide a time-bounded staging
window and run this procedure using the deployed API, callback worker, general
worker, PostgreSQL, broker, Redis, AWS STS/KMS/IAM and S3-compatible storage.
The owner must supply the non-secret target identifiers, exact image digests,
policy revisions and redacted evidence links, and must approve the legacy drain
window with the service/on-call owner.

If key migration across KMS keys is required, the owner must first authorize
and prioritize implementation of an explicit envelope rewrap lifecycle; it is
not implemented by the current key-provider adapter.

Until all gates have passing evidence and reviewer sign-off, mark Issue #214
open, keep `WORKFLOW_DURABLE_DISPATCH_ENABLED=false`, and do not claim staging
or production acceptance.
