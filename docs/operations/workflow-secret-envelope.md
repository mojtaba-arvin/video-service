# Workflow callback secret envelopes

## Trust boundaries

A callback URL is accepted only at the authenticated gRPC CreateJob boundary.
The API service encrypts it with a fresh AES-256 data key generated by AWS KMS.
The encrypted envelope is inserted in the same PostgreSQL transaction as the
Job, Workflow, Stage projections and immutable execution plan. The plan stores
only the opaque webhook_secret_ref; the broker receives only the Job and plan
identity tuple.

Redis Job details and Celery arguments must never contain the callback URL.
The legacy callback task now resolves the envelope at execution time and holds
the plaintext only in worker memory for the bounded HTTP delivery operation.

## Required configuration

Set these values in the API and worker environments:

- WORKFLOW_SECRET_KMS_KEY_ID: KMS key ARN or alias used for envelope encryption.
- WORKFLOW_SECRET_KMS_REGION: region containing the KMS key.
- WORKFLOW_SECRET_WORKER_ROLE_ARN_PREFIX: exact STS assumed-role ARN prefix
  for the callback worker, ending in /.

There is no plaintext fallback. CreateJob with a callback URL fails closed if
the KMS key is not configured or GenerateDataKey is denied. Worker resolution
fails closed if STS is unavailable, the caller ARN does not match the configured
prefix, the Job has no active envelope, the envelope is expired, or KMS
authentication fails.

## IAM separation

The API service role needs kms:GenerateDataKey for the configured key.
The callback worker role needs kms:Decrypt for the same key. Do not grant
kms:Decrypt to the public gRPC/API role unless its operational duties require
it. Restrict the worker role to the exact KMS key and require the authenticated
encryption context keys:

- purpose = webhook.callback
- algorithm = AES-256-GCM
- job_id, tenant_id, issuer, subject, and secret_id must be present.

Use kms:EncryptionContext:purpose and
kms:EncryptionContext:algorithm conditions plus
kms:EncryptionContextKeys in the key policy/IAM policy. Keep the worker role
separate from general-purpose Celery workers if practical; only the callback
worker needs decrypt permission.

## Operational constraints

- Never log callback URLs, ciphertext, wrapped data keys, or KMS request bodies.
- Never copy a decrypted callback URL into task kwargs, Redis, result backends,
  exception messages, traces, or metrics labels.
- Network egress policy and the callback URL validator remain mandatory; KMS
  authorization does not make a destination safe.
- Rotate/revoke by updating the Job secret record status; do not rewrite a
  previously accepted idempotent request with a new random envelope.
- Back up PostgreSQL metadata and retain the KMS key for as long as active
  envelopes must remain decryptable.

The STS ARN prefix check is an application-level guard, not a substitute for
least-privilege IAM. KMS key policy and role trust policy are the authoritative
cloud-side controls.
